# ML Pipeline

> Companion to the top-level [README](../README.md). All numbers in this
> document come from
> `mini-services/ml-service/metadata/transaction_models.json` and
> `mini-services/ml-service/metadata/nlp_models.json`, which are
> regenerated by `python3 train.py`. They are **not** hardcoded.

## Overview

The ML pipeline trains **7 models**:

- **3 transaction models** on PaySim: Logistic Regression, Random
  Forest, XGBoost. The XGBoost model is the **active** model used for
  live inference; LR and RF are kept as comparators for the Model
  Performance tab.
- **4 NLP models** on the message datasets: per-language `nlp_hi`,
  `nlp_hinglish`, `nlp_en`, plus a combined multilingual model
  `nlp_combined` with a 50-rows-per-template cap.

All 7 are stored as scikit-learn `Pipeline` objects (`StandardScaler` →
classifier for transactions; `TfidfVectorizer` → `LogisticRegression`
for NLP) in `mini-services/ml-service/models/*.joblib`.

## Transaction ML

### Features used (14 columns)

The transaction feature vector is identical across the three
transaction models. It is built by `derive_transaction_features()` in
`index.py` and the equivalent helper in `train.py`.

| # | Feature | Source | Type |
|---:|---|---|---|
| 1 | `amount` | raw PaySim | numeric |
| 2 | `oldbalanceOrg` | raw PaySim | numeric |
| 3 | `newbalanceOrig` | raw PaySim | numeric |
| 4 | `oldbalanceDest` | raw PaySim | numeric |
| 5 | `newbalanceDest` | raw PaySim | numeric |
| 6 | `orig_balance_change` | `newbalanceOrig − oldbalanceOrg` | derived |
| 7 | `dest_balance_change` | `newbalanceDest − oldbalanceDest` | derived |
| 8 | `amount_to_orig_balance` | `amount / oldbalanceOrg` (0 if denom=0) | derived |
| 9 | `amount_to_dest_balance` | `amount / oldbalanceDest` (0 if denom=0) | derived |
| 10 | `type_CASH_IN` | one-hot of `type` | categorical |
| 11 | `type_CASH_OUT` | one-hot of `type` | categorical |
| 12 | `type_DEBIT` | one-hot of `type` | categorical |
| 13 | `type_PAYMENT` | one-hot of `type` | categorical |
| 14 | `type_TRANSFER` | one-hot of `type` | categorical |

The `nameOrig` and `nameDest` PaySim columns are not used because they
are simulator-internal identifiers that would leak data, and because
they do not exist in real-world UPI transactions.

### Models and hyperparameters

| Model | Hyperparameters (from `transaction_models.json`) |
|---|---|
| `transaction_lr` | `LogisticRegression`, `scaler=StandardScaler`, `class_weight="balanced"`, `C=1.0`, `max_iter=1000`, `random_state=42`, **subsample_legit_rows=100000**, **subsample_keep_all_fraud=True** |
| `transaction_rf` | `RandomForestClassifier`, `n_estimators=200`, `max_depth=12`, `class_weight="balanced_subsample"`, `n_jobs=-1`, `random_state=42`, **subsample_legit_rows=100000**, **subsample_keep_all_fraud=True** |
| `transaction_xgboost` | `XGBClassifier`, `n_estimators=200`, `max_depth=6`, `learning_rate=0.1`, **`scale_pos_weight=105.0958`** (ratio of legitimate to fraud in the training split), `eval_metric="aucpr"`, `tree_method="hist"`, `random_state=42`, **subsample_legit_rows=null** (full 613,340-row training split) |

The `scale_pos_weight` for XGBoost is computed from the training
split's class imbalance:
`(607,559 legitimate) / (5,781 fraud) ≈ 105.0958`.

### Class imbalance handling

The training split is heavily imbalanced (0.94% fraud). The prototype
handles this with **class weighting, not oversampling**:

- `transaction_lr` — `class_weight="balanced"` (sklearn reweights
  classes inversely proportional to their frequency).
- `transaction_rf` — `class_weight="balanced_subsample"` (reweights
  per bootstrap sample).
- `transaction_xgboost` — `scale_pos_weight=105.0958`.

No oversampling (SMOTE / ADASYN / random) is performed before the
split, because that would leak minority-class samples into both train
and test. See [dataset.md](dataset.md) for the data-preparation rules.

### Evaluation metrics

For every transaction model, `train.py` computes:

- **Precision** (fraud-class), **Recall** (fraud-class), **F1** (fraud-class).
- **ROC-AUC** (binary).
- **PR-AUC** (average precision — far more informative than ROC-AUC on
  imbalanced data).
- **Confusion matrix** on the test split (10,099 rows, 1,252 fraud,
  8,847 legitimate), with `threshold=0.5`.

The XGBoost model's `3.0.0` version reflects two prior promotions —
both promotions happened during the verification run when the candidate
was retrained on identical training data (no drift window), which
yielded identical metrics and so the promotion rule (F1 ≥, recall ≥,
precision ≥ 0.95×) was trivially satisfied. When a real drift window
(validation steps 521–631) was added, the candidate was correctly
**rejected** (F1 dropped 0.9976 → 0.9968, precision dropped
0.9992 → 0.9944). See [drift.md](drift.md) for the adaptive-retrain
methodology and the rejection record.

### Why the XGBoost score is high — and what that means

PaySim is a **simulator** with clean, separable fraud patterns (e.g.
sudden large transfer with both origin and destination balance
anomalies). The high F1 reflects **the simulator's separability, not
real-world generalization**. The same model trained on real UPI data
— with its far noisier feature distributions and adversarial
fraudsters — would not achieve this score without substantial
feature engineering, graph features and adversarial training. This
is disclosed honestly throughout the UI and the documentation.

### Reproducibility

- **Random seeds set**: `numpy.random.seed(42)` (set in `train.py`
  before any sampling); `random_state=42` on every sklearn / XGBoost
  estimator; `random_state=42` on every `train_test_split` /
  group-aware split.
- **Model artifacts** are saved as `joblib` pipelines (the entire
  sklearn `Pipeline`, including the `StandardScaler` or
  `TfidfVectorizer`, so the same preprocessing is applied at
  inference time).
- **Metadata**: every model entry in
  `metadata/transaction_models.json` and `metadata/nlp_models.json`
  records:
  - `name`, `type`, `version`, `active`,
  - `dataset_version` (e.g. `paysim_v1`, `UCI_SMS_Spam_v1`),
  - `training_timestamp` (ISO 8601 UTC),
  - `features` (full list, in order),
  - `hyperparameters` (full dict),
  - `metrics` (precision / recall / F1 / ROC-AUC / PR-AUC /
    confusion_matrix / threshold),
  - `artifact` (path to `.joblib`).
- **Re-train** by running `python3 train.py` from
  `mini-services/ml-service/`. All metrics regenerate from the
  supplied data.

| `max_features` | 5,000 |

| `class_weight` | `"balanced"` |

| `random_state` | 42 |
| Split | group-aware 70 / 15 / 15 (duplicate-group aware, **label-stratified**) |

### Group-aware split — preventing template leakage

The NLP datasets have only ~20 unique templates each, repeated
500–1,000×. A naive random split would put the same template in both
train and test, inflating F1 from ~0.30 to a fabricated ~1.00.

The prototype's `group_aware_split` works in two phases:

1. **Group identical text strings** — every duplicate text string is a
   single "group" assigned as a unit to exactly one of train / val /
   test.
2. **Label-stratified** — within each label, split the groups 70 / 15 /
   15 with a min-1-in-test guard, so at least one legitimate and one
   scam template lands in the test set.

This was a real bug in an earlier version of the prototype: the
non-stratified group-aware split assigned all 5 legitimate Hindi
templates to the test set, causing the model to predict everything as
scam (F1 ≈ 0.39 / 0.30). The label-stratified fix recovered the honest
F1 numbers shown below.

### Combined multilingual model — 50-rows-per-template cap

The combined model trains on the union of Hindi, Hinglish and
English. Because the Hindi/Hinglish templates are repeated 500–1,000×
each, naively concatenating them with English's 3,591 unique
templates drowns English out and collapses the combined model to
"predict everything as scam" (F1 ≈ 0.20).

`train.py` mitigates this honestly by capping each template to **≤ 50
training rows** in the combined training split (test and validation
are untouched). This brings the combined F1 to **0.334** — still
limited by template scarcity, but with a balanced precision/recall
trade-off. The cap is recorded in
`metadata/nlp_models.json` under each model's `hyperparameters.split`.

### Honest interpretation (no generalization claims)

- **`nlp_hi` F1 = 1.000 — memorization, not generalization.** The
  test split contains 4 legitimate templates (1038 rows) and 7 scam
  templates (942 rows). The model has seen 4 of the 5 legitimate
  templates and all of the scam templates during training; the
  group-aware split assigned one legitimate template to validation
  and none to test. The test set is therefore a tiny in-distribution
  set that the model has effectively memorized. **This is not a
  generalization claim.**
- **`nlp_hinglish` F1 = 0.65 — the model cannot generalize from 4
  training legitimate templates to the 5th unseen one.** The test
  split contains 1 unseen legitimate template (1004 rows) and 7 scam
  templates (931 rows). The model predicts the unseen legitimate
  template as scam, so precision drops to 0.48 while recall stays at
  1.0. This is the honest outcome of the supplied data — the dataset
  has too few unique templates for the model to learn what
  "legitimate" looks like.
- **`nlp_en` F1 = 0.907 — honest real-world result.** The UCI SMS
  Spam Collection has 3,591 unique training templates and 834 test
  rows; the model generalises reasonably. The caveat is that UCI
  SMS Spam is general English spam/ham, not India-specific UPI scam
  vocabulary.
- **`nlp_combined` F1 = 0.334 — template scarcity drags the
  combined model down.** Even after the 50-rows-per-template cap,
  Hindi/Hinglish templates outnumber English templates in the
  combined training set, so the combined model over-predicts scam
  (recall 0.98, precision 0.20). This is the honest outcome of the
  supplied data and is disclosed in `/api/v1/models` and the
  dashboard.

These metrics are **not** hardcoded — they are the actual output of
`train.py` on the supplied data, and they regenerate from
`metadata/nlp_models.json` on every training cycle.

## Feature engineering for transactions — recap

See the [Features used (14 columns)](#features-used-14-columns) table
above. The four derived features are computed identically at training
time (in `train.py`) and at inference time (in `index.py::derive_transaction_features()`):

```python
orig_balance_change     = newbalanceOrig - oldbalanceOrg
dest_balance_change     = newbalanceDest - oldbalanceDest
amount_to_orig_balance  = amount / oldbalanceOrg if oldbalanceOrg else 0.0
amount_to_dest_balance  = amount / oldbalanceDest if oldbalanceDest else 0.0
type_<X>                = 1.0 if type == X else 0.0   # X in {CASH_IN, CASH_OUT, DEBIT, PAYMENT, TRANSFER}
```

These four derived features are the strongest SHAP contributors on
PaySim fraud predictions because they expose the simulator's
"originator emptied to zero, destination starts at zero" pattern
that flags synthetic fraud.

