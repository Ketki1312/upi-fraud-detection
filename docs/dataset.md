# Dataset Documentation

> Companion to the top-level [README](../README.md). All numbers in this
> document come from `mini-services/ml-service/metadata/dataset_audit.json`
> and `dataset_audit.md`, which are regenerated by `python3 audit.py`. They
> are **not** hardcoded.

## Critical Disclosure (Read First)

This prototype uses **three** datasets. None of them are real UPI banking
data, and none establish a causal transaction↔message relationship:

| Dataset | Type | Source |
|---|---|---|
| **PaySim** | Public **mobile-money simulator** dataset by Edgar Lopez-Rojas | Provided preprocessed as `PaySim_Preprocessed_Ready_for_ZAI.zip`. **PaySim is a SIMULATOR — it is NOT real UPI banking data.** |
| **Hindi** | Synthetic, marked `source=Synthetic` | `hindi_messages.csv` in the user upload. ~20 unique templates. |
| **Hinglish** | Synthetic, marked `source=Synthetic` | `hinglish_messages.csv` in the user upload. ~20 unique templates. |
| **English** | Public dataset, not collected by us | UCI SMS Spam Collection v1, auto-downloaded by `train.py` from the UCI archive. |

If the UCI download is blocked by the sandbox, the English model falls
back to `not_trained` and **no English data is fabricated**. The current
sandbox download succeeded, so English is `trained`.

## PaySim — Transaction Dataset

### Provenance

- **Author**: Edgar Lopez-Rojas.
- **Type**: Public mobile-money transaction **simulator** dataset
  (PaySim), provided as `PaySim_Preprocessed_Ready_for_ZAI.zip`.
- **Preprocessing on input**: already preprocessed by the dataset author
  / submitter — one-hot type columns, derived balance-change features
  and a chronological 70 / 15 / 15 split into train / validation / test
  CSVs. A `preprocessing_metadata.json` documents the original columns.
- **Disclaimer**: **PaySim is a PUBLIC MOBILE-MONEY SIMULATOR. It is NOT
  real UPI banking data and does not establish any causal
  transaction↔message relationship.** High fraud-detection F1 on PaySim
  reflects the simulator's clean synthetic fraud patterns, not
  real-world generalisation.

### Original PaySim columns (before preprocessing)

`step`, `type`, `amount`, `nameOrig`, `oldbalanceOrg`, `newbalanceOrig`,
`nameDest`, `oldbalanceDest`, `newbalanceDest`, `isFraud`,
`isFlaggedFraud`.

`step` is a PaySim time-step (1 hour of simulated time). `type` is one
of `CASH_IN`, `CASH_OUT`, `DEBIT`, `PAYMENT`, `TRANSFER`. `isFraud` is
the supervised label; `isFlaggedFraud` is the simulator's own (very
noisy) baseline rule and is not used in this prototype.

### Derived features (computed during preprocessing and at inference)

| Feature | Formula |
|---|---|
| `orig_balance_change` | `newbalanceOrig − oldbalanceOrg` |
| `dest_balance_change` | `newbalanceDest − oldbalanceDest` |
| `amount_to_orig_balance` | `amount / oldbalanceOrg` (0 if denominator is 0) |
| `amount_to_dest_balance` | `amount / oldbalanceDest` (0 if denominator is 0) |
| `type_CASH_IN`, `type_CASH_OUT`, `type_DEBIT`, `type_PAYMENT`, `type_TRANSFER` | One-hot of `type` |

### One-hot type columns

The five categorical values of `type` are one-hot encoded into the
columns above. The full feature vector used by the transaction models
has 14 columns (5 raw + 4 derived + 5 one-hot type). See
[ml.md](ml.md) for the exact list.

### Chronological 70 / 15 / 15 split

PaySim's chronological split is meaningful because `step` is time. The
training split contains the earliest 520 steps; validation contains
steps 521–631; test contains steps 632–743. This makes temporal drift
detection (PSI on later steps vs earlier steps) meaningful.

### Template scarcity (critical limitation)

The 10,000 rows are ~500–1,000× repetitions of only **~20 unique text
templates** (5 legitimate + 15–16 scam). The per-language Hindi model
honestly reflects this limitation:

- `nlp_hi` F1 = **1.000** — perfect on a 4-template test set. This is
  effectively **memorization of a tiny template set, not a
  generalization claim.**
- The model has never seen a held-out unseen template; the test split
  contains 4 of the 5 legitimate templates and a handful of scam
  templates that were also in training (because of how the group-aware
  split groups identical templates together and assigns groups 70 / 15 /
  15).

This limitation is disclosed in `/api/v1/models`, in the dashboard, in
the About / Dataset tab and in this document.

## Combined multilingual model — cap rule

The combined multilingual model trains on the union of Hindi, Hinglish
and English. Because the Hindi/Hinglish templates are repeated ~500–1,000×
each, naively concatenating them with English's 3,591 unique templates
drowns English out and collapses the combined model to "predict
everything as scam" (F1 ≈ 0.20).

To mitigate this honestly (without fabricating data), `train.py` caps
each template to **≤ 50 training rows** in the combined training split.
Test and validation splits are untouched. This brings the combined F1
to **0.334** — still limited by template scarcity, but with a balanced
precision/recall trade-off. The cap is disclosed in
`metadata/nlp_models.json` under each model's hyperparameters.

## Data audit results (consolidated)

The audit (`python3 audit.py`) writes both
`metadata/dataset_audit.json` (machine-readable) and
`metadata/dataset_audit.md` (human-readable). It records, per dataset:

- **Row counts** per split (PaySim) and per dataset (Hindi / Hinglish / English).
- **Duplicates** — both exact and normalized (whitespace + case
  collapsed) — so template repetitions are visible.
- **Missing values** per column.
- **Label distribution** (0 vs 1) and, where applicable, **category
  distribution** per dataset.
- **Type distribution** for PaySim (CASH_IN / CASH_OUT / DEBIT / PAYMENT / TRANSFER).
- **Temporal fraud-rate per 10-step window** for each PaySim split (used by the dashboard's trend chart).

## Dataset preparation rules

The prototype follows these data-preparation rules consistently:

1. **Preserve raw, create processed separately.** The raw CSVs in
   `mini-services/ml-service/data/raw/` are never modified. Train-time
   preprocessing (one-hot type, derived features, splits) is performed
   in memory or written to a separate processed CSV. PaySim's input
   file was already preprocessed by its submitter; the metadata JSON
   documents the original columns.
2. **Audit row counts / types / missing / duplicates / labels.** `audit.py`
   is run before every training cycle and writes both
   `metadata/dataset_audit.json` and `metadata/dataset_audit.md`.
3. **Prevent duplicate / template leakage via group-aware split.** For
   NLP datasets, identical text strings are grouped together and the
   group is assigned as a unit to exactly one of train / val / test.
   The split is also **label-stratified** within each label (within each
   label, split groups 70 / 15 / 15 with a min-1-in-test guard). This
   prevents a template from appearing in both training and test, which
   would otherwise inflate F1 from ~0.30 to a fabricated ~1.00 on
   Hindi.
4. **No oversampling before split.** Class imbalance is handled by
   class weighting (`class_weight="balanced"` for the LR / NLP models,
   `class_weight="balanced_subsample"` for RF, `scale_pos_weight` for
   XGBoost) — **not** by oversampling. This avoids leaking minority
   samples into both train and test.
5. **PaySim subsampling is documented per model.** The LR and RF
   transaction models are trained on a 100,000-legitimate-row +
   all-fraud-row subsample for efficiency. This subsampling is recorded
   in `metadata/transaction_models.json` under each model's
   `hyperparameters.subsample_legit_rows` and
   `hyperparameters.subsample_keep_all_fraud`. The XGBoost model is
   trained on the full 613,340-row training split (no subsampling).
6. **No fabricated data.** If a dataset is unavailable (e.g. UCI SMS
   Spam download blocked), the corresponding model is reported as
   `not_trained` and no synthetic replacement data is generated.
